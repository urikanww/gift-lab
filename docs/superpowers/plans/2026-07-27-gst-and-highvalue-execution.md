## Sequencing & risk

**GST is the spine — do Phase A strictly in order (1→2→3→4→5).** Task 3 depends on Task 1 helpers; Task 4 depends on Task 2 columns + Task 3 return shape; Task 5 depends on Task 4 persistence. **GST threads through these money sites:** PricingService `quoteTotals`/`quoteBreakdown` (Task 3), PriceEstimateController + AdminPriceBreakdownController (Task 3), QuoteService `createFresh`/`amend`/`retotalAfterReconfirm`/`reconfirmLine`/`issueInvoice` (Task 4), StripePaymentGateway unit_amount (reads GST-inclusive total, Task 8 — no re-derivation), CreditNote amount (reads GST-inclusive invoice.amount, Task 13), reorder create() path (Task 16).

**Depends on GST:** Task 13 and Task 16 read/produce the GST-inclusive total (functionally correct even mid-migration since they read `amount`/`total` verbatim, but land after Phase A to avoid asserting stale figures). Task 4 also carries the independent HIGH reconfirm-fee fix.

**Fully independent, parallelizable now:** Phase B (Tasks 6/7/8), Phase C (Tasks 9/10/11/12), Task 17. File-disjoint from GST and from each other except: Task 9 and Task 12 both edit `AppServiceProvider::boot()` (sequence them or merge the boot edits); Task 6 and Task 7 both touch `AdminBlankCaptureController`/`routes/api.php` (do 6 then 7).

**Internal ordering within Phase D:** 14a (tracking-number uniqueness) is a prerequisite for 14c reship; 13 (void+credit) is a prerequisite for 14c cancel_credit and for the amend-VOID guard. Order 13 → 14a → 14b → 14c. Task 15 shares `QueueService` advance() with 14c — coordinate the two QueueService edits.

**Riskiest tasks:**
1. **Task 14a (tracking-number-per-job)** — load-bearing courier correctness; `forQuote` determinism is baked into ShipmentService + webhook correlation, and reship (14c) can't work until it lands. Touches live shipping. Highest blast radius.
2. **Task 4 (GST snapshot + reconfirm fee fix)** — the rate-snapshot discipline and subtotal-DELTA vs full-recompute interaction across four retotal sites is subtle; the folded reconfirm-fee fix changes real billed figures. Every existing money assertion shifts.
3. **Task 13 (void + credit)** — CRITICAL money-loop with atomicity, cascade, and idempotency requirements; the VOID-invoice re-anchor guard and payment_state reconciliation are easy to miss.
4. **Task 8 (Stripe)** — global/static CurlClient mutation + idempotency-key param-drift (400 on total mismatch) are footguns; double-charge is the failure mode.
5. **Task 6 (SSRF)** — must cover redirect re-validation on every hop and the CIDR/mapped-IPv6 cases the PHP flags miss, or the guard is theatre.

Lowest risk / quick wins to front-load for a green baseline: **Task 17** (CI), **Task 7** (route gate), **Task 11** (prune), **Task 10** (enrich job).
